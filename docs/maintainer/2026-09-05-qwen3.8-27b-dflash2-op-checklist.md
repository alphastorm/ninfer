## 1. 范围与完成含义

当前问题是将 checkpoint 推荐配置 `block_size=8` 误用为 Op 数学域、kernel 索引和性能域。
本轮要完成受影响合同、wrapper、workspace query、dispatch、kernel、独立 oracle 和 benchmark
的对应修正，并对已有合法 routes 在新产品点重新 qualification。所有实现继续由原 Op family
拥有，不添加 target-private 平行路径，也不按 K 建立不同的 public Op。

本文逐项列出 37 个 Op/profile 工作项。OP-01..08 必须修改合同/实现并重新 qualification；
OP-09..32 已具有所需 extent，需复核数值/状态与性能并按证据修改原 routes；OP-33..37 为
准备、提交相关的直接复用项，重点验证新宽度的可观察行为，不要求无依据地重写或调优。
表格中一个 Op 的多个已注册格式均属于该项，关闭时分别说明其验证结果。

旧 K=7 的实现和测量可作为同点基线，不能沿用“全域已完成”的结论。下文列出的现有阈值
用于定位待比较的分界，不是重新调优后的固定方案。没有测量支持时，不宣称某个候选更快。

正式 Engine schedule、binder 接线、Program state/workspace composition、Graph inventory 和
端到端 acceptance/吞吐属于后续集成。本文只要求 Op 自身在代表性合法输入上可独立调用、
验证和 capture/replay。改变运行 K 不要求重新下载 source、转换 artifact、repack 权重或
引入新的量化格式。

## 2. 统一 workload、索引与数值边界

### 2.1 运行 extent

| 符号 | 含义 | 支持范围 |
|---|---|---|
| B | active requests | 1..8 |
| K | 启动选定的 draft count | 1..15，推荐 7 |
| W | proposal/verify 物理 block width | K+1，2..16 |
| T | backbone/target matrix columns | W*B，最大 128 |
| U | mask-head/selector matrix columns | K*B，最大 120 |
| P_b | 每请求可验证 draft extent | 0..K |
| Q_b | target live input columns | P_b+1 |
| A_b | accepted draft count | 0..P_b |
| L_b | provisional output count | A_b+1 |
| N_b | Frontend 最终提交数 | 0..L_b |
| W_c、B_c | context materialization 物理布局 | decode W_c=1..16、B_c=1..8；prefill W_c=1..2048、B_c=1 |
| T_c | context projection columns | W_c*B_c；prefill 最大 2048 |
| N_lane | pending-feature lane capacity | startup-fixed 1..8，且 >=B |
| S_state | StateImage slot capacity | startup-fixed，覆盖本轮 state selectors |

同一 Engine 的物理 W 由选定 K 决定；不能为全部配置计算有效 W=8 或 W=16 来规避扩展。
Proposal attention 可使用 valid_columns=W，target attention/GDN 使用 Q_b，context append
使用 counts=N_b。W_c 是 pending storage/gather extent，不能由 accepted draft count 替代；
all-accept 会提交 K+1 个 target input rows，必须保留最后一行 feature。

性能输入域以 `{(K+1)*B}` 和 `{K*B}` 的实际乘积集合定义。纯矩阵 Op 可以按相同列数去重；
卷积、attention、GDN 和状态 Op 必须保留 W/B 划分以及 device counts。已有 Linear 类 Op 的
任意正 T 合同继续成立；最大 128/120 是本轮产品性能范围，不是这些合同的新上限。

### 2.2 固定模型 geometry 与张量布局

```text
hidden H=5120; MLP I=17408; target feature H_f=25600
draft Q=32*128=4096; K/V=8*128=1024; five local layers; window/capacity=2048
conv groups=320; group width=16; taps=2; sides=2
selector candidates M=16; rank R=256
physical vocab=248320; valid global ids=0..248076; optimized head rows=131072

proposal residual       BF16 [5120,W,B]
finish_delta            BF16 [320,2,W,B]
packed mask hidden      BF16 [5120,U]
candidate ids/scores    I32/FP32 [16,K,B]
projected selector h    BF16 [256,K,B]
drafts / proposal q     I32 [K,B] / FP32 [16,K,B]
target logits           BF16 [248320,W,B]
pending features        BF16 [25600,W,N_lane]
```

Artifact Weight `[N,C]` 表示 `[output rows,input columns]`；runtime Tensor 的 ne[0] 连续。
Base kernel 保留 artifact `[side,tap,channel]=[2,2,5120]`，runtime view 为 `[5120,2,2]`；
codebook 保留 artifact `[vocab,rank]`，runtime view 为 `[256,248320]`。这些固定 8/16/256
等模型维度不能随运行 W/K 一起替换。

### 2.3 保持的数学与实现自由度

- Dynamic convolution 仅在当前 request block 内跨相邻位置，位置零没有 previous tap；
  finish 消费同一 prepare 的 output-side delta，无跨轮卷积状态。
- Proposal SWA 为 `abs(key_position-query_position)<2048`；当前 block 的有效 query 互相
  可见。Q/K 使用 plain head RMSNorm 和 theta=1e7 的 full-D128 split-half 1-D RoPE。
- Final norm-pack 跳过 anchor；top-16 使用 score 降序、同分 global-id 升序。Optimized
  head 的 row id 先映射为 global id，再供 selector 使用。
- Selector 是实际前驱条件下的逐位 walk；保留实际抽样的 FP32 q。逐 row、部分预计算、
  完整 lattice 均可作为同一 Op 的内部方案，不能换成独立逐位置 unary argmax 或 Viterbi。
- Sparse accept 使用实际 q 的 p/q rejection 和 `(p-q)+` correction；N 而非 P/A/L 决定
  最终持久状态提交。Proposal RNG purpose 与 target accept/correction/bonus 分离。
- Norm/conv prepare、projection/conv/residual、norm/RoPE、norm/pack、projection/top-k、
  selector walk 和五层 context materialization 保持闭合 public 边界。Private staging、
  reduction、tiling、launch 数由 qualified route 决定，不要求每个融合 Op 只有一个 kernel。
- Oracle 从 represented public inputs 及精确解码的 stored weights 计算完整公式；不可观察
  中间精度作为 implementation profile。OP-07 已去掉 raw K 的额外语义舍入；最终 BF16 K、
  `FP16_RNE(BF16)` V storage cast、public BF16 outputs 和实际 FP32 q 保持各自边界。

## 3. 必须修正合同和实现的 Ops

### OP-01 — rmsnorm_dynamic_grouped_conv_prepare

`src/ops/wrapper/dynamic_grouped_conv.cpp`、`src/ops/dynamic_grouped_conv/bf16/`。

已修正的问题：合同和 wrapper 固定 W=8；plan 仅按 B 选择 split-K。Partial kernel 将八列 MMA tile
与 request batch 绑定，reduce 的 128 threads 正好只处理 8*16 个位置/通道。

- [x] 将 residual/prepared 改为 `[5120,W,B]`、finish_delta 改为 `[320,2,W,B]`，支持 W=2..16；
  workspace query 显式接收宽度域和 batch 域，和执行共用 route/layout 事实。
- [x] 分离 contraction 的 T 分片和卷积的 W 边界，改齐 partial/reduce 索引、shared storage、
  非满 tile 和线程覆盖；比较 split-K、norm staging/融合及 coefficient reduction 方案。
- [x] 从完整 norm→projection→input-conv 公式验证两个 public outputs；覆盖所有 W、不同 B、
  非零前一 request 末列和新 route seams；测完整 Op 的 launch 与 workspace 成本。

完成证据：RTX 5090、CUDA 13.1、Release/sm_120a。独立 FP64 oracle 覆盖全部 120 个 W/B

scope 归还及 query high-water 均通过。W/B=3/3、7/7、14/7、16/8 另通过同址双次 Graph replay。

比较了六组 tiling/split 方案及其 RMS 缩放因子后置的两节点融合版本，共12个完整 Op 候选。
两种算术 profile 均先通过 oracle；保留 norm staging 的三节点方案更快，未采用的实例和

R32/C32/split-4；97..128 使用 R32/C64/split-4。最大 workspace 为 2,621,440 bytes。

Public benchmark 已改为实际捕获 Graph，使用256 MiB L2 flush、8 warmup/60 repeats，遍历

### OP-02 — linear_dynamic_grouped_conv_add

合同同 OP-01。落点：`src/ops/dynamic_grouped_conv/w8/` 和公共 wrapper。

- [x] 支持 x `[C,W,B]`、residual `[5120,W,B]` 和匹配 delta；按真实 request 内位置断开 tap。

- [x] 重选小 T 与 65..128 列的 contraction；比较 private materialized projection 与融合

- [x] 独立解码 signed W8/FP16 scales 后计算完整公式，检查 residual 原地更新、跨 request
  边界和 scope 归还。若采用 materialized route，原始 payload 为 `5120*W*B*2` bytes，
  最大 1.25 MiB；有额外 scratch 的其他 routes 分别计入实际 query。

### OP-05 — linear_topk（三个 head profiles）

合同：[linear_topk.h](../../include/ninfer/ops/linear_topk.h)。落点：`src/ops/linear_topk/`。

问题：Wrapper 从 U%7 推断 B，workspace 只查询 B；kernel 只覆盖旧 `7,14,...,56` 集合。
W8/FP8/Q4 的若干 launcher 在未命中时直接调用固定 56 列实例，放宽 wrapper 会错误读写。

- [x] 将 public contract 定义为逐矩阵列独立的 projection-top16，hidden `[5120,U]`，

  重建完整 dispatch、masked tail、column tiling 和 merge，删除将任意列数送入旧 exact
  instance 的分支。不得只补 U=120 或保留固定七列的平行 public overload。

合同：[candidate_selector.h](../../include/ninfer/ops/candidate_selector.h)。落点：

问题：合同、strides 和 kernel 七步展开固定 K=7；每 request 一个 512-thread CTA 的调度
只在旧宽度有证据。原先将“只算 realized row”固定为唯一 production 方案限制了比较范围。

- [x] 从输入读取 K=1..15，改齐 `[16,K,B]`、`[256,K,B]`、`[K,B]` 的索引和循环；
  保留固定 M=16/R=256，以及 `(seed,F+i,DFlash2ProposalPurpose)` 的位置 RNG。

- [x] 独立 FP64 lattice oracle 再执行条件 walk，检查实际前驱下的 q；覆盖混合温度、

### 4.1.1 OP-09 — feature Linear qualification

## 6. Qualification 执行要求

### 6.1 正确性与 route 覆盖

- [ ] OP-01..08 的公共合同、wrapper、执行域和 capacity query 一致。既有 tests/bench fixtures
  改为显式 K/W/B，删除固定推荐宽度是唯一合法输入的断言，不建立兼容 aliases。
- [ ] 对有宽度语义的 Ops，所有支持 W 至少有代表性正确性覆盖；补 B=1/B=8、奇数宽度、
  非满 tile 和相同 T 不同 `(W,B)`，例如 `(W=8,B=2)` 与 `(W=4,B=4)`。矩阵重归约的
  oracle 覆盖每条新生产 route 和其实际分界，不用完整模型输出替代。
- [ ] 状态/稀疏采样项覆盖 device counts 与 physical width 分离、P=0/K、N=0/L、首次/中途
  拒绝和 all-accept；FP32 q 与 token/state effects 分别验证。确定性 codec、copy、索引
  用 exact criterion，浮点公式用声明的数值 criterion，不要求不同 K 产生同一 draft。
- [ ] 每个新增或改变的 workspace route 验证同址 Graph capture/replay、scope lifetime 和
  query 上界。Capacity 取区间内所有可达 routes 的最大值，不能只测最大 K/B 一个点。

### 6.2 性能比较与记录

在 RTX 5090、sm_120a、CUDA 13.1 上排他进行 GPU 计时。编译采用 `cmake --build <dir> -j`。
沿用适用的 public Op benchmark、CUDA Graph 与明确的 cache 条件，计入完整 Op 的所有
launch、scratch 读写和后处理；不把 isolated contraction 的改进直接标成 fused Op 改进。

先用短 K、推荐 K=7、最大 K=15、B=1/B=8 及会改变选路的 seams 区分候选，再补足最终
routes 在实际产品域的曲线。对 state/attention 保留 W/B/context/counts 维度，对纯矩阵按
T/U 去重。只在一个 kernel 已由 benchmark 识别、且 kernel-level 答案会改变当前选择时使用
ncu；本阶段不要求尚未接入的 Engine 或 nsys 作为前提。

每项关闭时只记录相关 geometry/format、K/W/B 或列数、context/counts、选定 route、
representative latency、数值/状态检查结果和必要限制。对实现未变且证据已覆盖的项目注明
复用依据；不要求重复所有旧实验，不从 K=7 的历史数据声称 K=15 性能已通过。

### 6.3 顺序与本阶段退出条件

1. 先落实 OP-01..08 的 extent/数学合同及对应 oracle；workspace 接口与执行一起修正。
2. 优先处理会错误索引的 conv、top-k、context 和 accept，随后用完整 Op measurement
   重选重投影/head、context materialization 和 target attention/GDN/MLP 的关键 routes。
3. 完成 OP-09..32 的逐项复核和 OP-33..37 的行为验证；对未修改的小 Op 按实际风险控制证据。
